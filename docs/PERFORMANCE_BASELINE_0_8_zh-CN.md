# PsyReaSFX 0.8 性能基线

## 测试环境

- 日期：2026-09-01
- 系统：Windows 10.0.19045
- 逻辑处理器：16
- .NET：8.0.29
- 数据：`tools/generate_hardening_library.py` 生成的 5,000 个确定性短 WAV，包含重复候选、多声道文件和独立 Artwork 目录
- 流程：完整目录索引 → 新 SQLite 数据库首次保存 → 相同快照再次保存 → 完整载入 → 内存搜索

测试数据位于系统临时目录，不属于发布包，也不包含用户素材。

## 首次基线

| 阶段 | 时间 |
|---|---:|
| 索引 | 5,241.4 ms |
| 完整保存 | 8,313.2 ms |
| 完整载入 | 28.4 ms |
| 内存搜索 | 0.46 ms |
| 托管内存增量 | 12.05 MiB |

结论：搜索和载入不是当前瓶颈；首次扫描的音频读取有优化空间，最明显的问题是完整保存。

## 第一项优化：批量读取旧路径身份

来源重定位检查原先针对每个素材单独执行一次 SQLite 查询。改为一次载入全部 `asset_id → path` 后在内存比较，仍在同一事务中迁移发生变化的引用。

| 阶段 | 优化后 | 相对首次基线 |
|---|---:|---:|
| 索引 | 4,658.6 ms | -11.1%（受文件缓存影响，仅供参考） |
| 完整保存 | 6,553.0 ms | -21.2% |
| 完整载入 | 26.9 ms | -5.3% |
| 内存搜索 | 0.54 ms | 绝对值仍低于 1 ms |
| 托管内存增量 | 12.05 MiB | 无变化 |

完整 Desktop 自检（包括路径迁移冲突回滚）在优化前后均通过。

## 第二项优化：按素材身份增量保存

Desktop 保存不再清空并重建 `assets`。保存前一次载入现有素材，以稳定的 `asset_id` 比较新旧记录：只写新增或有变化的素材，只删除快照中已经不存在的素材；路径移动仍会在同一事务中迁移收藏、试听历史、集合、Region、响度和项目使用记录。索引器已经生成的素材身份和相对路径会直接复用，不再在保存循环中重复推导。

| 阶段 | 增量保存后 | 相对首次基线 |
|---|---:|---:|
| 索引 | 5,201.6 ms | 文件缓存会影响该项，仅供参考 |
| 首次保存 5,000 条 | 1,644.3 ms | -80.2% |
| 相同快照再次保存 | 56.5 ms | -99.3% |
| 完整载入 | 25.2 ms | -11.3% |
| 内存搜索 | 0.45 ms | 绝对值仍低于 1 ms |

第二次保存的写入审计为：改动 `0`、跳过 `5,000`、删除 `0`。完整自检新增了这一行为断言，并继续覆盖重复 `asset_id` 导致的事务回滚，防止增量优化静默吞掉身份冲突。

## 第三项优化：后台串行写入与请求合并

Desktop 的素材快照、组织、试听活动、元数据、Region、响度和工程使用记录现在共享同一个后台写入队列。这样即使 SQLite 的异步 API 同步完成，也不会占用 WPF UI 线程；多个写入不会再争抢同一个数据库。组织结构在短时间连续变化时只保存最新快照，等待较早请求的调用方会在最新快照安全落盘后一并完成。

自动压力检查连续提交 64 次组织保存，结果为实际执行 `1` 次、合并 `63` 次，数据库最终内容与第 64 次请求一致。试听活动原有的 900 ms 脏集合合并继续保留，并接入同一串行队列。
